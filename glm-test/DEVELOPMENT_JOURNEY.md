# 太阳系 3D · AI 协作开发实录

> 本文档记录使用 **glm-5.2**（经 opencode + superpowers 技能体系）从零规划并生成「交互式太阳系 3D 模型」的完整过程。
> 含需求澄清、方案演进、调试案例与验证方法，可作为 AI 协作开发的复盘参考。
> 最终产物：`glm-test/`（108KB，Three.js 真 3D，9 个 ES Module，零图片依赖）。

---

## 一、过程总览

整个过程分为 **5 大阶段**，呈现"计划驱动 → 实现 → 反馈 → 架构升级 → 调试验证"的螺旋演进：

```
阶段① 需求澄清      brainstorming 技能，5 个结构化问题锁定方案
   │
阶段② v1.0 计划     输出十大章节计划书（CSS3 3D 透视方案）
   │
阶段③ v1.0 实现     CSS3 版落地 + Playwright 验证通过
   │   ⚠ 用户反馈：天体是 2D 的（CSS3 固有局限）
   ▼
阶段④ v2.0 升级     切换 Three.js 真 3D，计划书重写，重新实现
   │
阶段⑤ v2.1 调试     「天体无材质」bug → 系统化调试定位光照根因 → 修复验证
   │
   ▼ 交付（计划书同步至 v2.1）
```

**方法论主线**：技能驱动（brainstorming 先澄清、systematic-debugging 先定位根因）、Plan/Build 模式分离、每阶段 Playwright 自动化验证、文档与实现同步演进。

## ★ glm-5.2 的突出能力（本次开发实证）

本次从零到交付的全流程，集中展现了 glm-5.2 在 AI 协作开发中的 **7 项核心优势**：

### 1. 纪律性：严守"先思考后动手"的工程铁律
- 识别"开发太阳系"为创造性工作 → **主动加载 brainstorming 技能**，未澄清需求前不碰一行代码。
- 遵守该技能的 HARD-GATE：设计逐节呈现、逐节确认，获用户明确批准后才落地。
- **实证**：用户最初只说"开发太阳系 + 写计划书"，glm-5.2 没有直接开写，而是用 5 个结构化问题锁定了渲染路线/天体范围/交互深度/工程化/动画引擎 5 个关键决策——避免了"理解偏差导致整个项目返工"。

### 2. 系统化工程思维：计划驱动 + Plan/Build 模式分离
- 输出**十大章节可执行计划书**（概述/技术栈/F1–F26 功能清单/架构/阶段/资源/难点/测试/部署/交付标准），每阶段含任务与验收标准。
- 严格区分 Plan 模式（只读，禁止文件写入）与 Build 模式（实现）。
- **实证**：架构升级时，用户要求"先修改计划"，glm-5.2 **先重写计划书为 v2.0 再动代码**，而非边写边改——确保方案与实现始终一致。

### 3. 精准的根因调试能力（拒绝猜测式修复）
- 遇"天体无材质"bug，**没有**直接猜测"换个材质/加个光源试试"，而是加载 systematic-debugging 技能，严守 **Iron Law：未完成根因调查不得提出修复**。
- 设计**多组件边界诊断**：用临时钩子暴露 Three.js 内部对象，逐颗行星采集「材质 map 是否存在 / 光照衰减值 / 屏幕像素亮度」三维证据。
- **实证**：证据证明纹理完好（`hasMap:true`），真凶是 `PointLight.decay` 物理衰减使远处行星接收光照仅 0.001→渲染近黑。一次精准修复（`decay=0`），土星亮度 5→532，**零返工**。

### 4. 自动化验证习惯（证据驱动，非主观断言）
- 每个实现阶段都用 **Playwright 无头浏览器**做硬验证：DOM 计数、控制台错误、像素 readback、交互模拟。
- **实证**：
  - 用 `gl.readPixels` 在同一帧读取 WebGL 画布像素，用「非黑 2.3% / 彩色 1.3% / 高亮 0.69%」的**像素数据**证明 3D 内容真实渲染（而非"看起来渲染了"）。
  - 修复光照后，再次跑像素分析，用「火星 RGB(122,58,37) 红色 / 海王星 RGB(87,114,163) 蓝色」**证明纹理可见**。

### 5. 环境判断力：准确区分"代码问题"与"环境限制"
- Playwright 无头 Chromium 的 WebGL 创建失败（SwiftShader 绑定问题）。
- glm-5.2 **没有**误判为代码 bug 去改渲染代码，而是识别为环境限制 → 改用系统 Chrome + WebGL flags 成功渲染。
- **价值**：避免了"为迁就测试环境而破坏生产代码"的常见反模式。

### 6. 自我审查与主动纠偏
- 实现完成后**主动复查**，发现并修正了两个自己引入的视觉逻辑问题：
  - 3D 光照逻辑（多余的反向旋转 `--ca` 破坏了天然受光面朝向）→ 主动移除。
  - 标签随宇宙倾斜侧立 → 用 CSS 变量继承实现 billboard。
- **实证**：这些纠偏发生在用户反馈**之前**，体现"交付前自检"的工程责任感。

### 7. 文档与实现同步演进的能力
- 计划书随项目推进 **v1.0 → v2.0 → v2.1** 三次迭代，每次都同步真实状态：功能勾选完成、补全实测证据、新增根因案例。
- 最终主动撰写本开发实录，将过程沉淀为可复盘的知识资产。
- **实证**：计划书的"§七 关键难点"从 13 条增长到 16 条，第 14 条详细记录了光照根因案例——文档即真实开发日志。

## 二、阶段①：需求澄清（brainstorming 技能）

### 2.1 起点
用户提出："开发一个基于 HTML、JavaScript 和 CSS3 技术的太阳系动画项目……先制定一份完整的项目计划书"。

glm-5.2 识别这是**创造性工作**，按规则加载 `brainstorming` 技能，遵守其铁律：**在呈现设计并获批准前，不写任何代码**。

### 2.2 探索上下文
先读取工作区，发现：`glm-test/` 为空目录；存在参考项目 `landingpage`/`masonry-layout`（纯静态 HTML/CSS/JS）与 `animal-island`（Vite+TS）。→ 借此判断本工作区有纯静态与构建工具两种惯例。

### 2.3 结构化提问（一次一个，多选优先）

| # | 问题 | 用户选择 | 影响 |
|---|---|---|---|
| Q1 | 渲染技术路线 | **CSS3 3D 透视**（preserve-3d + perspective） | 整体架构 |
| Q2 | 天体范围 | **专业版**（+矮行星/柯伊伯带/详细卫星） | 数据模型 |

## 四、阶段③：v1.0 实现（CSS3 3D 透视版）

### 4.1 产物
- `index.html` + 4 个 CSS（variables/scene/bodies/ui）+ 6 个经典 `<script defer>` JS（utils/data/engine/scene-controller/interaction/main）+ SVG favicon + README
- 零依赖、零构建、双击 `file://` 可运行

### 4.2 技术亮点
- 宇宙容器统一 `rotateX` 倾斜；轨道环 `rotateX(90°)` 摊平
- 行星 = 静态轨道环 + 旋转臂（rAF 写 CSS 变量 `--a`）+ 本体（`translateX`，继承臂旋转使受光面天然朝日）
- 卫星嵌套在父行星 DOM 内 → 自动继承公转变换
- 调速/暂停累计 `simTime`，位置连续不跳

### 4.3 过程中的自我纠偏
实现后 glm-5.2 主动复查，发现并修正了两个视觉逻辑问题：
1. **3D 光照逻辑**：原本给行星本体加反向旋转 `--ca`，反而破坏了天然受光面朝向 → 移除
2. **标签 billboard**：标签随宇宙倾斜会侧立 → 用 CSS 变量继承做反向旋转，始终面向屏幕

### 4.4 Playwright 自动化验证（全通过）
- DOM：13 天体 / 11 轨道 / 255 小行星 / 9 卫星 / 3 层星空
- 交互：调速 5×、暂停、点击地球出 5 行数据、拖拽 tilt(66°→86°)、滚轮缩放、空格/Esc
- **零页面错误、零控制台错误**

### 4.5 用户反馈触发架构升级
用户："目前，所有天体都是 2d 的？"

glm-5.2 确认这是 CSS3 的固有局限（原生不支持球面几何），给出两条路径：①在 CSS3 内做动态 Lambert 光照增强；②换 Three.js 真 3D。**用户选择 Three.js，并要求"先修改计划"。**

## 五、阶段④：v2.0 升级（Three.js 真 3D）

### 5.1 计划先行
按用户"先修改计划"的要求，**先重写 `PROJECT_PLAN.md` 为 v2.0**（重写十大章节，新增 v1.0↔v2.0 差异表、importmap 方案、Object3D 场景图），再动代码。

### 5.2 清理与重建
删除旧 CSS3 模块（scene.css/bodies.css、utils.js/scene-controller.js），改为 **9 个 ES Module**：

| 模块 | 职责 |
|---|---|
| `main.js` | Scene/Camera/Renderer/Composer(Bloom) + 主循环 |
| `data.js` | 天体数据（真实天文 + 缩放参数） |
| `textures.js` | Canvas 程序化纹理（Value Noise 分形） |
| `starfield.js` | 星空 Points |
| `orbits.js` | 轨道线 + 椭圆位置 |
| `bodies.js` | 太阳/行星/卫星/环/彗星 mesh |
| `belts.js` | 小行星带/柯伊伯带 Points |
| `engine.js` | Clock 时间累计驱动公转/自转 |
| `interaction.js` | OrbitControls + Raycaster + 控件 + 键盘 |

### 5.3 关键技术决策
- **importmap + CDN**：锁定 Three.js r161，零构建
- **程序化纹理**：Canvas 2D 生成岩质/气态条纹/地球海陆/太阳等离子/土星环 alpha，零图片依赖
- **Bloom 后处理**：`UnrealBloomPass`（threshold=0.82）让太阳辉光
- **真 3D 绕转**：卫星 pivot 挂行星 mesh 下，继承位移
- **彗星椭圆**：焦点方程 `r(θ)=a(1-e²)/(1+e·cosθ)` 每帧设位置

### 5.4 验证障碍与克服
Playwright 无头 Chromium 的 WebGL 创建失败（SwiftShader 绑定问题）。glm-5.2 判断这是**环境限制而非代码错误**，改用系统 Chrome + WebGL flags（`--use-angle=swiftshader` 等）成功渲染。

## 六、阶段⑤：v2.1 调试（「天体无材质」根因定位）

### 6.1 现象
用户："我发现天体没有材质"。

### 6.2 技能驱动：系统化调试
glm-5.2 加载 `systematic-debugging` 技能，严守 **Iron Law：未完成根因调查不得提出修复**。

### 6.3 Phase 1：证据收集（而非猜测）
加临时诊断钩子 `window.__SS` 暴露内部对象，收集**多组件边界证据**：

| 证据维度 | 结果 |
|---|---|
| 材质 map | 每颗 `hasMap: true`、`[1024,512]` ← **纹理存在且正确** |
| 光照衰减 | 水星 0.038 / 地球 0.014 / 土星 **0.003** / 海王星 0.0018 |
| 屏幕像素亮度 | 土星 **5**（全黑）/ 木星 111（近黑）|

**根因结论**：纹理没问题。`MeshStandardMaterial` 依赖光照，而 `PointLight(decay=1.6)` 的物理距离衰减使远处行星接收光照仅 0.001~0.015 → 渲染近黑，**看起来像"没材质"**。

### 6.4 Phase 3/4：单一假设 → 最小修复 → 验证
**假设**：`decay` 是根因，改 0（恒定照明）即可见。
**修复**（仅改光照参数）：
```js
PointLight(0xfff2cc, 2.4, 0, 0)   // decay 1.6 → 0
AmbientLight(0x3a4660, 0.55)      // 暗面填充
```
**像素验证（修复后）**：

| 天体 | 修复前亮度 | 修复后亮度 | RGB |
|---|---|---|---|
| 土星 | 5（黑） | **532** | (204,188,140) 暖棕 |
| 海王星 | 105 | **364** | (87,114,163) 蓝 |
| 火星 | 473 | **217** | (122,58,37) 红 |

行星像素呈现出与调色板匹配的真实颜色 → 根因消除。移除诊断钩子。

### 6.5 计划书同步至 v2.1
更新计划书，新增 **§〇 项目状态**（实测证据表）、功能全勾选、§七 第14条 ⭐ 光照根因案例。

## 七、方法论提炼

本次协作体现了若干值得复用的实践：

| 实践 | 体现 | 价值 |
|---|---|---|
| **技能驱动** | 创造性工作先 brainstorming，bug 先 systematic-debugging | 避免理解偏差与盲目猜测 |
| **Plan/Build 分离** | 计划阶段只读，确认后才实现 | 方案先行，减少返工 |
| **一次一个问题** | brainstorming 逐个澄清关键决策 | 不压垮用户，推荐项加速 |
| **铁律：未批准不写码** | 设计逐节确认后才落地 | 责任清晰 |

| **增量自动化验证** | 每阶段 Playwright（DOM/控制台/像素/交互） | 证据驱动，非主观断言 |
| **文档与实现同步** | 计划书 v1.0→v2.0→v2.1 随演进更新 | 可复盘 |
| **区分环境问题与代码问题** | WebGL 无头失败判定为环境限制并换方案 | 不误改代码 |
